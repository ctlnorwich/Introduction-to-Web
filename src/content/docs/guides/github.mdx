## What is Git?

Git is a widely-used **distributed version control system**. It was created in 2005 by [Linus Torvalds](https://github.com/torvalds), who also created the Linux operating system. Git is used by software developers to manage codebases, track and review changes, and work collaboratively within teams.

Codebases can be complex collections of maybe hundreds or thousands of files that reference each other in varying ways. A version control system like Git is pretty much essential when multiple people are working on the same codebase at the same time, since it records who did what, when they did it and whether there are any conflicting changes that need to be resolved.

## How Git works

Git works by storing version history in a **repository** or 'repo' (essentially, a hidden `.git` directory which contains all the version control data). This repository can be entirely local to the developer's computer, or synced to a remote online copy using a service such as GitHub. A repository can have multiple **branches**. Each branch contains a version of the codebase that can be used for a specific purpose: for example, to create new feaures, test updates, fix bugs in isolation, or try out alternative ways of doing things. Branches can be be merged into one another to add the changes from one branch to another. The primary branch is usually called the `main` branch, but naming is flexible. In addition to branches, **tags** are often used to keep track of version numbers for different releases. More complex projects often have many branches: for example, the popular website builder, [Astro has over 400 branches and 2900 tags!](https://github.com/withastro/astro)

Saving changes to a branch, is called a **commit**. This is a bit like when you save your progress to a slot in a video game. 

Commits should at least have a summary message, but can also have a more detailed description about what has changed. There are different conventions for writing commit messages, but no universal standard. One popular way is begin with a verb in the present tense and imperative mood - e.g. `Add about.html` or `Fix styling issue with dropdown`. Another more complex specification is [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).

The git repository data is saved to a hidden directory inside your project directory (visible if you enable e.g. 'show hidden files'). If you delete this directory, the repository will no longer exist locally. 

## Git in the terminal

You can use Git directly from the command line or terminal if you want to, providing it is insalled on your computer. Many versions of MacOS come with a version of Git pre-installed: type `git version` or `git -v` into the terminal to check if you have it!

<Steps>

1. Create a new folder called `my-git-project`.

2. Open the project folder in VS Code.

3. Open the terminal in **VS Code** (Terminal > New Terminal).

4. Use the terminal to create a new `readme.md` file:

    ```bash
    touch readme.md
    ```

5. Check git is installed on your machine:

    ```bash
    git -v
    ```

6. Initialise a new git repository:

    ```bash
    git init
    ```

7. Edit the readme file in VS Code (e.g. add `# Project Information` at the top to create a heading).

8. Stage all files for commit (there's only one file at the moment):

    ```bash
    git add .
    ```

9. Commit the changes to the readme file with a message (summary):

    ```bash
    git commit -m "Initial commit"
    ```

10. Check if there is anything further to commit (there shouldn't be):

    ```bash
    git status
    ```

</Steps>

Congratulations! You've used Git in the Terminal! The directory which contains your project will aslo contain a hidden `.git` directory. You'll only see this directory (or a ghostly version of it) if you enable 'show hidden files' in your operating system. If you delete this `.git` directory, you will delete the git repository, along with the project history, but you _won't_ delete the project itself – the most recent version of the project will remain intact.

## GitHub
[GitHub](https://github.com/) is currently the most popular platform for hosting and managing online Git repositories. Many software projects treat GitHub as a centralised online 'source of truth' for the codebase, with individual developers cloning the repo from GitHub to their local machine, pulling down the latest changes, then pushing the changes back to GitHub when they're ready. GitHub has always been a separate entity from the Git Open Source project and it is now owned by Microsoft. There are alteratives to GitHub such as [GitLab](https://about.gitlab.com/) or [Bitbucket](https://bitbucket.org/)

## GitHub Codespaces
[GitHub Codespaces](https://github.com/features/codespaces), accessible from you GitHub account, allows you to run a virtual machine along with VS Code in the cloud so you can do all your web development in your web browser. This is useful in cases where you are unable to set up the necessary tools on your machine, or you are using a tablet instead of a laptop or desktop computer. When you visit a GitHub repo, you can click on the green __Code__ dropdown to either clone the code to your local machine or 'spin up' a virtual machine Codespace to work on it in the cloud (each codespace will have a unique name). There are some restrictions to what you can do in a Codespace versus a local development environment, mainly around server-side applications. Since Codespaces use a cloud-hosted version of VS Code, you will need to mangage your Git repo via VS Code's Source Control feature (see below).

## GitHub Desktop
[GitHub Desktop](https://desktop.github.com/download/) is an optional app that allows you to manage your local and remote Git repositories from an easy-to-use GUI. While you can also manage your Git repositories directly in VS Code using the sidebar GUI (also avoiding the need to memorise terminal commands), you may still prefer the simpler and separate experience of GitHub Desktop.

- After connecting your GitHub account, you can **push** your repository changes to the online GitHub 'origin', where others can view your code.
- If your changes are on a sepearte branch, they can then be reviewed and **merged** into another branch by yourself or another collaborator. You can prompt a collaborator to do this by creating a **pull request**.
- You can also **fetch** updates others have made, and review them before **pulling** them into your branch.

## GitHub in VS Code
VS Code has a built in Git client via the [Source Control](https://code.visualstudio.com/docs/sourcecontrol/overview) icon in the left sidebar. While the UI is a little less user-friendly than GitHub Desktop, it is more convenient to use since you can see your Git status along with your code all in one place. You will need to have Git installed on your machine for this to work, but you won't need to use the command line. We recommend that you familiarise yourself with this way of doing things for day-to-day use.

## Things to practise

### Clone a repo:
Let's clone the following repo from GitHub (use [VS Code's Source Control](https://code.visualstudio.com/docs/sourcecontrol/quickstart#_option-a-clone-a-repository-locally) for this): [https://github.com/ctlnorwich/Portfolio-Website-Example](https://github.com/ctlnorwich/Portfolio-Website-Example)

### Fork a repo
If we've cloned a repo we don't have permission to make changes to _directly_, we have the option to create a fork instead. A Fork is new, distinct version of the entire repository that shares code and visibility with the original. With a fork, we can use someone else's repo as a starting point for our own ideas. You have the option to preserve a connection 'upstream' back to the orignial repo, either to pull new features from the original or to create pull requests from your fork for the orignal owner to review and incorporate back into the original.

### Create a new repo
Let's create a repository from scratch. You can either do this locally and push to GitHub, or create the repo in GitHub first and clone it locally. We will create a README.md file for the repository. Typically, the README.md file is used to provide an overview of the project along with some examples and basic 'getting started' documentation (in-depth documentation is best created elsewhere). the `.md` file extension stands for [Markdown](https://www.markdownguide.org/) – an efficient language for formatting text documents, which has become the standard for authoring technical documentation and is also popular for blogging and longform writing.

### Create a branch
It's good to get into the habit of creating branches to manage different aspects of your code. If you are unsure about your code, having a `develop` branch for work in progress or experimentation without changing anything on your `main` branch can be easier than commiting your half-finished or experimental code to your `main` branch and then having to revert that branch to an earlier commit if it doesn't work. This is essential when you are working on project where the `main` branch is the production version of your code, or in a bigger team where the `main` branch should only contain code which has been tested and approved by the lead developer.

### Push, Pull and Merge
If you work on a codebase with multiple developers, you will eventually run into an issue where your local copy of a branch must be merged with the remote version on GitHub. This is not just because you have added your changes to the branch, but that someone else has added their changes while you were working and you need to pull these down and merge them with your own. Sometimes the merge can be automatic, but if you have both edited the same file, there will be a merge conflict and you will have to manually choose which parts to keep ('resolve the conflict'). Thankfully, VS Code and GitHub Deskop offer visual editors to help you do this. [How to deal with merge conflicts in VS Code](https://code.visualstudio.com/docs/sourcecontrol/merge-conflicts).


## GitHub Pages
The GitHub Pages feature allows you to host a single static website from a public repository of you choice. Static sites are composed of a collection of 'static' files (html, css, js and maybe some media files), unlike dynamic sites, which run code on a server and connect to a database of some kind. We can configure Pages in the settings for our repo once we've published it.
